# Требования к фронтенду (для ИИ-ассистента, который пишет код)

**Версия:** 1.1, 04.10.2026. **API:** `docs/openapi.yaml` 0.3.0, словарь `dict-v2.1`. **Утверждено:** капитан команды — Вита.

Документ описывает **только то, что бэкенд уже отдаёт**: экран «Находки» (список пациентов), карточку пациента с протоколом и находками, добавление находок через словарь и поиск. Маршруты, уведомления и трекинг пока не реализованы в бэкенде. Их места в макетах нужно оставить, но не подключать (раздел 8).

Макеты: `Переделать.png` — список, `Переделать-1.png` — карточка пациента. Визуальный стиль берётся из макетов: зелёный акцент, оранжевый для выбранного пункта меню и отмены, карточки со скруглением, светло-серый фон. Где данных из макета в API нет, поле **не выдумывать и не заполнять заглушками**, а скрывать (раздел 7).

---

## 1. Как устроена система (для понимания)

```
МИС → ML (читает протокол УЗИ, находит находки) → бэкенд (правила словаря: к кому и в какой срок) → фронт (врач подтверждает)
```

- Пациенты и протоколы **создаются только из результатов ML**. Фронт их не создаёт и не редактирует.
- ML предлагает находки со статусом `SUGGESTED`. Врач их подтверждает (`CONFIRMED`), отклоняет (`REJECTED`) или добавляет свои (`MANUAL`, сразу `CONFIRMED`).
- Срочность и специалиста определяет бэкенд по словарю. Фронт **только показывает** `level`, `targetSpecialty` и `targetDays` и сам ничего не вычисляет.

## 2. Подключение к API

- Базовый адрес — переменная окружения, по умолчанию `http://localhost:8080`. CORS для `/api/**` открыт для любого origin.
- Живая документация: `http://localhost:8080/swagger-ui.html`. Проверка связи: `GET /api/ping` → `{"status":"ok"}`.
- Даты: `date` приходит как `YYYY-MM-DD`, `date-time` — ISO 8601 в UTC. Показывать в формате макета: `02.10.2026 · 08:41`, в часовом поясе браузера.
- Ошибки: тело `{ "code": "FINDING_NOT_FOUND", "message": "..." }`. Код `400` означает неверный запрос (показать `message` в тосте), `404` — не найдено (в карточке показать экран «Пациент не найден»).
- `doctor` во всех действиях врача — ФИО текущего пользователя из нижнего левого угла макета. Авторизации пока нет: на демо имя задаётся константой.
- **Демо-данные.** При пустой базе бэкенд загружает 10 пациентов («Пациент 001» … «Пациент 010»). Пациенты 008 и 009 экстренные: в списке они стоят первыми.

## 3. Справочники для отображения

### 3.1. Уровень срочности `level` / `maxLevel`

| Значение | Подпись | Вид |
|---|---|---|
| `EMERGENCY` | Экстренно | Красная метка (бейдж и полоска слева у строки или карточки). Строка всегда наверху (сортирует бэкенд) |
| `URGENT` | Срочно | Янтарная / оранжевая метка |
| `PLANNED` | — | Без метки |
| `null` | — | Без метки (у пациента нет активных находок) |

Красный (`#E5484D` или близкий) использовать **только** для экстренного уровня и просрочки. Оранжевый из макета уже занят под «выбрано» и «отклонить», поэтому для `URGENT` лучше взять янтарный оттенок, отличимый от него.

### 3.2. Флаги `flags`

Элемент: `{ code, name, note, setBy }`. Показывать бейджем с текстом `name` (русское название уже приходит с бэкенда), а `note` выводить во всплывающей подсказке. Если `name` нет, показать `code`.

| `code` | Где | Как показать |
|---|---|---|
| `DISCREPANCY` | находка, протокол | Бейдж «РАСХОЖДЕНИЕ» (жёлтый): находка есть в описании, но не в заключении |
| `INCOMPLETE` | находка | Бейдж «НЕПОЛНОЕ ОПИСАНИЕ» |
| `NO_CONCLUSION` | протокол | Баннер над протоколом: «В протоколе нет заключения — нужна ручная проверка» |
| `PREP_VIOLATED`, `OUTDATED_TERM`, `INCORRECT_TERM`, `TEMPLATE_NORM` | протокол, находка | Нейтральный серый бейдж |
| `SYSTEM_UNKNOWN`, `SYSTEM_CONVERTED` | находка (щитовидная железа) | Серый бейдж, пояснение в `note` |
| `MINOR` | находка | Бейдж «НЕСОВЕРШЕННОЛЕТНИЙ» |
| `MERGED_GYNECOLOGY` | находка | Серый бейдж «ОБЪЕДИНЕНО»; в `note` — с какой находкой объединена |

Неизвестный код показывать нейтральным бейджем, а не падать.

### 3.3. Тип исследования `studyType`

| Значение | Подпись |
|---|---|
| `PELVIS_FEMALE` | УЗИ органов малого таза |
| `ABDOMEN` | УЗИ органов брюшной полости |
| `BREAST` | УЗИ молочных желёз |
| `THYROID` | УЗИ щитовидной железы |
| `PROSTATE` | ТРУЗИ предстательной железы |
| `LOWER_LIMB_VESSELS` | УЗДС сосудов нижних конечностей |
| `KIDNEY` | УЗИ почек |
| `SOFT_TISSUE` | УЗИ мягких тканей |

### 3.4. Статусы

| Поле | Значения и подписи |
|---|---|
| `Finding.status` | `SUGGESTED` — «Ждёт подтверждения», `CONFIRMED` — «Подтверждена», `REJECTED` — «Отклонена», `REMOVED` — не показывать |
| `Finding.source` | `ML` — ничего не писать, `MANUAL` — пометка «добавлено врачом» |
| `Patient.reviewState` | `PENDING` — «Новые», `ATTENTION` — «Требует внимания», `OK` — проверено |
| `Protocol.status` | `DONE` — обычный, `FAILED` — «Протокол не прочитан» (показать `error.message`), `ANNULLED` — «Протокол аннулирован» (серым) |
| `NotTriggered.reason` | `NEGATION` — «отрицание в тексте», `NORMAL` — «норма», `POST_SURGERY` — «после операции», `BELOW_THRESHOLD` — «ниже порога, маршрут не нужен», `OUT_OF_SCOPE` — «вне словаря» |

| Шейка матки | `CERVICAL_POLYP`, `CERVICAL_RETENTION_CYSTS`, `ENDOCERVICITIS` |
| Яичник | `OVARIAN_LESION`, `OVARIAN_TORSION`, `OVARIAN_APOPLEXY`, `PCOM`, `LOW_OVARIAN_RESERVE` |
| Маточная труба / придатки | `ECTOPIC_PREGNANCY`, `TUBO_OVARIAN_ABSCESS`, `HYDROSALPINX` |
| Вены малого таза | `PELVIC_VARICOSE_VEINS` |
| Анамнез | `AMENORRHEA_HISTORY` |
| Желчный пузырь | `GALLSTONES`, `GALLBLADDER_POLYP`, `ACUTE_CHOLECYSTITIS`, `GALLBLADDER_HYDROPS`, `BILIARY_SLUDGE`, `CHRONIC_CHOLECYSTITIS` (для `GALLSTONES` с `location: choledoch` — «Холедох») |
| Печень | `HEPATIC_STEATOSIS`, `LIVER_HEMANGIOMA` |
| Толстая кишка | `COLON_DIVERTICULA` |
| Брюшная полость / малый таз | `FREE_FLUID` |
| Молочная железа | `BREAST_LESION` |
| Щитовидная железа | `THYROID_NODULE`, `THYROID_DIFFUSE_AIT`, `THYROID_ENLARGEMENT` |
| Вены нижних конечностей | `DEEP_VEIN_THROMBOSIS`, `SUPERFICIAL_THROMBOPHLEBITIS`, `POST_THROMBOTIC_CHANGES`, `VENOUS_INSUFFICIENCY`, `SAPHENOUS_DILATION` |
| Артерии нижних конечностей | `ARTERIAL_STENOSIS` |
| Мягкие ткани | `SOFT_TISSUE_INFLAMMATION` |
| Брюшная стенка / паховая область | `HERNIA` |
| Почка | `HYDRONEPHROSIS`, `KIDNEY_STONES` (для `location: ureter` — «Мочеточник») |

Таблицу держать в одном файле-константе, а для неизвестного кода показывать «—».

### 3.6. Атрибуты находки (подписи)

`attributes` — свободный объект. Показывать до 3–4 самых важных атрибутов строкой под названием находки, например «18 мм · FIGO 1 · подозрение». Если ключа нет в таблице ниже, не показывать его.

| Ключ | Подпись |
|---|---|
| `sizeMm` | `N мм` |
| `count` | `×N` или текст как есть |
| `uncertain: true` | «подозрение» (курсивом) |
| `birads`, `orads`, `tirads`, `figo` | `BI-RADS N`, `O-RADS N`, `TI-RADS N`, `FIGO N` |
| `volumeMl`, `residualUrineMl` | `N мл` |
| `volumeCm3`, `ovaryVolumeCm3` | `N см³` |
| `distanceToJunctionMm` | `N мм до соустья` |
| `maxStenosisPct` | `стеноз N%` |
| `incarcerated: true` / `false` | «ущемление» (красным) / «без ущемления» |
| `functional: true` | «функциональная» |
| `menopause: true` | «менопауза» |

## 4. Экран «Находки» — список пациентов (`Переделать.png`)

Пункт меню «Находки». Это рабочий список врача.

### 4.1. Данные

`GET /api/patients?search=&reviewState=&studyType=&maxLevel=&dateFrom=&dateTo=&page=0&size=20` → `{ items: PatientShort[], page, size, total }`.

Сортировку делает бэкенд: сначала `EMERGENCY`, потом `URGENT`, внутри уровня — новые сверху. Фронт порядок **не меняет**.

### 4.2. Чипы-фильтры над таблицей

| Чип в макете | Что делать |
|---|---|
| «Все N» | Без фильтра; число = `total` |
| «Новые N» | `reviewState=PENDING`; число = `total` этого запроса |
| «Экстренные N» | `maxLevel=EMERGENCY`; число = `total` этого запроса |
| «Требует внимания N» (нет в макете — добавить вместо «Просрочена запись») | `reviewState=ATTENTION` |
| «Просрочена запись», «Без записи» | Нужны маршруты — не показывать (раздел 8) |

Счётчики: при открытии экрана параллельно четыре лёгких запроса с `size=1` (без фильтра, `reviewState=PENDING`, `maxLevel=EMERGENCY`, `reviewState=ATTENTION`), число берётся из `total`. Фильтры комбинируются с поиском. После действий врача в карточке список и счётчики при возврате перезапрашиваются.

### 4.3. Колонки строки

| Колонка в макете | Откуда |
|---|---|
| Чекбокс | В API нет групповых действий для нескольких пациентов — **скрыть** |
| Пациент: ФИО, «N лет», дата рождения | `fullName`, `age` (склонение: «1 год / 2 года / 5 лет»), `birthDate` |
| Метка срочности | `maxLevel` (раздел 3.1): красная полоска слева и бейдж «Экстренно» рядом с ФИО |
| Находка: название / тип исследования / дата | Строка 1 — `topFindings[0].name` (если `activeFindings > 1` — «+N» серым, N = `activeFindings − 1`); бейдж уровня `topFindings[0].level`. Строка 2 — тип исследования `studyType` (раздел 3.3). Строка 3 — `receivedAt` (`02.10.2026 · 08:41`). При пустом `topFindings` строка 1 — «Без находок» |
| Направление (вместо «Этап») | `topFindings[0].targetSpecialty` и срок `targetDays` («немедленно» / «N дней»), как в карточке (5.3). Это не этап маршрута, а куда направит система |
| Статус (вместо «Срок записи», «Уведомлён») | Бейдж `reviewState` («Новые», «Требует внимания», «Проверено») и «ждут подтверждения: N» (`pendingFindings`) |

Клик по строке открывает карточку пациента (`/patients/{id}`).

### 4.4. Поиск и фильтр

- Поле «Поиск» и кнопка «Найти» → `search` (по ФИО и `externalId`). Enter тоже запускает поиск.
- Иконка фильтра открывает поповер с полями: тип исследования (`studyType`, список из раздела 3.3) и период по дате исследования (`dateFrom`, `dateTo`).

### 4.5. Состояния

Загрузка — скелетон из 4 строк. Пустой список — «Пациентов не найдено» и кнопка сбросить фильтры. Ошибка сети — сообщение и кнопка «Повторить».

## 5. Карточка пациента (`Переделать-1.png`)

Маршрут `/patients/{id}`. Данные: `GET /api/patients/{id}` → `PatientCard`:

```
{ patient: PatientShort, currentProtocol: ProtocolShort | null, currentFindings: Finding[], routes: [], history: { protocols, findings, routes } }
```

Полный текст протокола и `notTriggered`: `GET /api/protocols/{currentProtocol.id}` → `{ protocol, patientId, text, modelVersion, error, findings, notTriggered }`.

Оба запроса выполняются параллельно при открытии карточки и заново после каждого действия с находкой (или карточка обновляется из ответа действия).

### 5.1. Шапка пациента

| Поле в макете | Откуда |
|---|---|
| ФИО (в три строки) | `patient.fullName` |
| id с кнопкой копирования | `patient.externalId` (ID в МИС) |
| Возраст | `patient.age` |
| Дата рождения | `patient.birthDate` |
| Пол | `patient.sex`: `F` → «Женский», `M` → «Мужской» |
| Email, телефон, СНИЛС, рост, вес, ИМТ, группа крови, «Подробнее» | В API нет — **скрыть** (раздел 7) |

Если у пациента `maxLevel == EMERGENCY`, над шапкой показать красный баннер: «Экстренная находка: {name} — {targetSpecialty}». Данные взять из первой находки с `level == EMERGENCY` в `currentFindings`.

### 5.2. Блок «Протокол исследования»

- Заголовок: «Протокол исследования», рядом серый чип с датой `protocol.receivedAt` (`13.07.2026 · 13:14`) и подпись типа исследования (раздел 3.3).
- Флаги протокола (`protocol.flags`) — бейджи под заголовком. При `NO_CONCLUSION` — баннер (раздел 3.2).
- `status == FAILED`: вместо текста — карточка «Протокол не удалось прочитать» с `error.message`. `ANNULLED`: серый баннер «Протокол аннулирован в МИС».
- **Текст:**
  - Если `text` не `null`, показать его целиком с сохранением переносов строк (`white-space: pre-wrap`) в серой карточке, как в макете.
  - Если `text == null`, показать только `protocol.conclusion` с подписью «Заключение» и пометкой «Полный текст недоступен».
- **Подсветка** (оранжевая заливка в макете). Для каждой находки из `findings` (кроме `REMOVED`):
  - если есть `evidence.start` и `evidence.end`, подсветить `text.slice(start, end)`;
  - если позиций нет, найти в тексте (или в заключении) первое вхождение `evidence.text` без учёта регистра и подсветить его;
  - если не нашлось, не подсвечивать.

  Цвет подсветки зависит от статуса: `SUGGESTED` — оранжевый (как в макете), `CONFIRMED` — светло-зелёный, `REJECTED` — без подсветки. Для экстренной находки — светло-красный.
- **Связь с находками.** Наведение на строку находки подсвечивает её фрагмент ярче и прокручивает протокол к нему. Клик по фрагменту в тексте прокручивает к строке находки.
- **«Почему не сработало».** Под текстом свёрнутый блок со списком `notTriggered`: название (`name` или `code`), причина (раздел 3.4), цитата `evidence.text`. Для `BELOW_THRESHOLD` можно показать `attributes` (например, «3,6 мм»). Это объяснимость для врача и жюри, поэтому блок обязателен, пусть и свёрнутый.

### 5.3. Блок «Находки»

Источник — `currentFindings`. Порядок: сначала `EMERGENCY`, затем `URGENT`, затем остальные; внутри — `SUGGESTED` перед `CONFIRMED`, затем `REJECTED`.

Строка таблицы:

| Колонка | Содержимое |
|---|---|
| Орган | По таблице 3.5, со стороной |
| Находка | `name`; под ним строка атрибутов (3.6) и бейджи `flags` (3.2); для `MANUAL` — пометка «добавлено врачом» |
| Направление (добавить) | `targetSpecialty` · срок: `targetDays == 0` → «немедленно», 1 → «1 день», N → «N дней», 180 → «6 месяцев», 365 → «12 месяцев». Бейдж `level` (3.1). Если `targetSpecialty` пустой, показать «—» |
| Кнопки | Зелёная ✓ и оранжевая ✕ (как в макете) |

Действия:

| Действие | Запрос | Поведение |
|---|---|---|
| ✓ Подтвердить | `PATCH /api/findings/{id}` `{ "status": "CONFIRMED", "doctor": "..." }` | Строка становится «подтверждённой» (зелёная отметка, кнопки сменяются на «Отменить») |
| ✕ Отклонить | `PATCH /api/findings/{id}` `{ "status": "REJECTED", "doctor": "...", "comment": "..." }` | Опциональное поле «Причина» во всплывающем окне. Строка бледнеет, название зачёркнуто, подсветка в протоколе исчезает |
| Отменить решение | `PATCH` с противоположным статусом (`CONFIRMED` ↔ `REJECTED`) | Вернуть в `SUGGESTED` API не умеет — кнопка просто меняет решение |
| «Подтвердить все» (добавить над таблицей, если есть ≥ 2 `SUGGESTED`) | `POST /api/patients/{id}/findings/confirm` `{ "findingIds": [...], "doctor": "..." }` | Все `SUGGESTED` → `CONFIRMED` |
| Изменить находку (иконка карандаша при наведении) | `PATCH /api/findings/{id}` `{ "code": "...", "attributes": {...}, "comment": "..." }` | Смена кода → бэкенд заново подставит специалиста и срок по словарю |
| Удалить (в меню строки, только для `MANUAL`) | `DELETE /api/findings/{id}?reason=...` | Строка исчезает (на бэкенде мягкое удаление) |

После любого действия перезапросить карточку (или заменить строку объектом из ответа) и пересчитать подсветку.

### 5.4. «+ Добавить» находку

Модальное окно:
1. **Поиск по словарю:** `GET /api/dictionary/findings?studyType={currentProtocol.studyType}&q={ввод}`. Показывать `name`, рядом метку, если `maxLevel == EMERGENCY` («может быть экстренной»). Переключатель «все типы исследований» убирает параметр `studyType`.
2. **Поля:** сторона (необязательно; левая / правая / обе → `attributes.side`), размер в мм (необязательно → `attributes.sizeMm`), комментарий.
3. **Сохранить:** `POST /api/patients/{id}/findings` `{ "code", "protocolId": currentProtocol.id, "attributes", "comment", "doctor" }` → `201`, находка сразу `CONFIRMED`, `source: MANUAL`.

Специалиста и срок для ручной находки бэкенд ставит по умолчанию из словаря. Фронт их не спрашивает.

### 5.5. Правая колонка «История приёмов»

Источник — `history.protocols` (прошлые протоколы пациента, новые сверху).

| Строка в макете | Откуда |
|---|---|
| Дата · время | `receivedAt` (`13.07.2026 · 13:14`) |
| Заголовок | тип исследования (3.3); у `ANNULLED` — с пометкой «аннулирован» |
| Подзаголовок | `findingsCount > 0` → «Находок: N», иначе «Без находок»; у `FAILED` — «Не прочитан» |
| Стрелка | Открыть протокол: `GET /api/protocols/{id}` в модальном окне или боковой панели, только чтение (текст с подсветкой, находки, «почему не сработало») |

Подтверждённые находки прошлых протоколов (`history.findings`) показать компактным списком «Ранее подтверждено» под историей: название и дата.

Если записей больше 8, показывать первые 8 и кнопку «Подробнее» (раскрывает остальные). Пустая история — «Других исследований нет».

### 5.6. Блок «Маршрут»

Маршрутов в API пока нет: `routes` всегда пустой. Показать заголовок «Маршрут» и серую подпись «Маршрут будет составлен после подтверждения находок» без кнопки «Добавить» (раздел 8).

## 7. Чего в API нет — скрывать, не выдумывать

- **Пациент:** email, телефон, СНИЛС, рост, вес, ИМТ, группа крови, номер карты (`cardNumber` всегда `null`).
- **Список:** этап маршрута, прогресс, срок записи, уведомления, групповой выбор.
- **Карточка:** маршрут и его шаги, «Подробнее» в шапке.

Если в макете под эти данные есть место, его нужно убрать или сжать вёрстку, а не оставлять «—». Исключение — колонка «Направление» у находки: там «—» допустим.

## 8. Позже (не делать сейчас)

Маршруты (`/api/patients/{id}/routes`, `/api/routes/{id}`), уведомления («Пуш»), трекинг (`GET /api/routes`), а вместе с ними колонки «Этап», «Срок записи», «Уведомлён» и чипы «Просрочена запись» / «Без записи».
