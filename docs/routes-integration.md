Обновлено 05.10.2026. Дополнение из `reviews/routes-reference-2026-10-05`
встроено в Java-бэкенд. ML-контракт и медицинский словарь сохранены.
Новая карточка подключена к API ниже; визуальная и браузерная проверка описана
в [отчёте по карточке](patient-card-integration.md).

## Поведение

После разбора всех находок протокола бэкенд группирует подтверждённые находки
по специалисту и создаёт маршруты. При изменении, отклонении, удалении находки,
исправлении и аннулировании протокола маршруты пересчитываются. Уже завершённые
маршруты не возникают повторно при редактировании комментария. Перенаправление
врачом к другому специалисту сохраняется.

Поддерживаются ближняя, срочная и наблюдательная цепочки, запись, перенос,
неявка, шесть тактик врача, госпитализация, процедура, контроль и закрытие.
Экстренная находка сразу запускает эскалацию персоналу; ручная подтверждённая
находка также участвует. Пока эскалация открыта, сообщения пациенту запрещены.

Сообщения, задачи, таймеры, маршруты, журнал и обработанные события хранятся
в PostgreSQL. Повтор события с тем же `eventId` и содержимым возвращает
`200`, `applied: false`; другое содержимое с тем же ID — `409 EVENT_ID_CONFLICT`.
Изменения сериализуются транзакционной блокировкой PostgreSQL, включая
таймеры и приём ML, чтобы параллельные запросы не создавали дубли.

При ошибке таймера его транзакция откатывается целиком; он остаётся `PENDING`
и повторяется при следующем проходе. Ошибка пишется в серверный лог. Постоянно
ошибающийся первый таймер требует исправления причины: следующие таймеры
не обгоняют его. Перемотка исполняет обработчики с временем их наступления,
поэтому каскад таймеров обрабатывается хронологически.

Старые подтверждения не мигрируются в маршруты массово при старте. Для такого
пациента повторный `POST /api/patients/{id}/findings/confirm` с его актуальными
находками выполнит сверку. Новые подтверждения и результаты обрабатываются сразу.

## Подключение новой карточки

Запросы врача используют действующую cookie-сессию. POST/PATCH/DELETE требуют
`X-CSRF-TOKEN`, полученный через `/api/auth/csrf` после входа.

| Назначение | Метод и адрес |
|---|---|
| Карточка | `GET /api/patients/{patientId}` |
| Все маршруты пациента | `GET /api/patients/{patientId}/routes` |
| Маршрут, этап, сроки, история, задачи, запись | `GET /api/routes/{routeId}` |
| Список маршрутов с фильтрами | `GET /api/routes?open=true&stage=BOOKED` |
| Шаблоны для кнопки отправки | `GET /api/notification-templates` |
| Отправка по шаблону | `POST /api/routes/{routeId}/notifications` |
| История сообщений | `GET /api/patients/{patientId}/notifications` |
| Сообщения конкретного маршрута | `GET /api/routes/{routeId}/notifications` |
| Слоты заглушки расписания | `GET /api/schedule/slots?routeId=…` |
| Запись в слот | `POST /api/schedule/bookings` |
| Задачи и их выполнение | `GET /api/tasks`, `POST /api/tasks/{taskId}/done` |
| Эскалации | `GET /api/escalations?patientId=…&open=true` |
| Действия по эскалации | `POST /api/escalations/{id}/accept`, `/contacted`, `/close` |
| Журнал | `GET /api/patients/{patientId}/journal` |

В карточке новые данные находятся в `clinicalRoutes`, закрытые —
в `history.clinicalRoutes`. `banner` содержит предупреждение о незавершённом
маршруте. `patient.activeRoutes` — фактическое число открытых маршрутов.
Старые `routes` и `history.routes` остаются пустыми для совместимости
с прежними клиентами. Новая карточка использует **clinicalRoutes**;
операций ручного создания и редактирования устаревших шагов в ней нет.
В этом модуле этапы меняются событиями МИС и тактикой врача.

Пример тела запроса кнопки отправки:

```json
{"templateCode":"REMINDER_24H","confirm":false,"doctor":"Координатор"}
```

Первый успешный ответ — `201` с сообщением. Если пациенту уже отправляли сообщение
за последние 24 часа, ответ — `409 CONFIRM_REQUIRED`. Только после подтверждения
пользователем повторить запрос с `confirm:true`. Автоматические сообщения
откладываются с учётом общего лимита на пациента, включая параллельные маршруты.
`400 TEMPLATE_CONTEXT_REQUIRED` означает, что выбранному шаблону не хватает
данных текущего этапа (например, срока контрольного визита).

## События внешних систем

`POST /api/integration/route-events` принимает новый контракт `RouteEvent`.
Он отделён от `/api/integration/events`, который по-прежнему передаёт DOCX в ML.

```json
{
  "eventId": "mis-route-event-001",
  "type": "BOOKED",
  "routeId": "UUID маршрута из API",
  "slotId": "id из /api/schedule/slots"
}
```

`POST /api/integration/crm/callbacks` принимает статусы `SENT`, `DELIVERED`, `READ`,
`FAILED` либо ответы `BOOK`, `CALLBACK_REQUEST`, `OTHER_ORGANIZATION`, `NOT_PLANNING`.
Поздний статус `SENT` не сбрасывает прочтение. Воронка засчитывает уведомление
по доставке/прочтению первого сообщения маршрута, не по созданию записи в БД.
Несоответствие пациента маршруту, слота специальности и недопустимые переходы
отклоняются. Дата госпитализации передаётся как `YYYY-MM-DD` и сохраняется.

## Запуск и границы заглушек

```powershell
cd C:\hackaton\final
docker compose up --build -d --wait
```

`ROUTES_ENABLED=true` включает слушатели, таймеры и API маршрутов.
`ROUTES_ENABLED=false` отключает их, сохраняя приём ML и прежнюю карточку.
`ROUTES_SIM_ENABLED=false` по умолчанию скрывает перемотку и сценарии.
В `compose.verification.yaml` симулятор включён; он тоже требует сессии и CSRF.
Модельное смещение времени существует только в памяти процесса: перезапуск
сбрасывает его. Демо-перемотку и сброс использовать только на отдельной базе.

Тексты, интервалы, лестница эскалации и расписание задаются в
`backend/src/main/resources/routing/route-config.yaml`. Изменения применяются
после перезапуска. `ROUTES_CONFIG` позволяет задать альтернативный ресурс
при обычном запуске Java; для внешнего файла в Docker также нужен bind mount.

**Реальной доставки push/SMS пока нет.** Отправка создаёт запись в локальной
заглушке CRM. В демо она видна через `GET /api/sim/crm/outbox`; в обычном режиме —
через историю уведомлений пациента. Поля `patientExternalId`, `preferredChannel`,
`fullText`, `shortText`, `links` и `buttons` подготовлены для будущего адаптера.
Ссылки `sm-clinic.example` и врачи расписания — демонстрационные.
Расписание не является бронированием ресурсов настоящей МИС.
Машинные интеграционные API доступны без пользовательской сессии, как и прежний
ML callback; текущий Docker публикует порты только на localhost.

Статичный дашборд фронтенда не подключён к новым `/api/dashboard/*`.
В БД применяется существующая схема проекта `ddl-auto=update`; для развёртывания
вне хакатона потребуются версионированные миграции и реальный CRM/МИС-адаптер.

## Воспроизводимая проверка

```powershell
cd C:\hackaton\final
docker compose -p meditron-verification -f docker-compose.yml -f compose.verification.yaml up --build -d --wait
.\ml\.venv\Scripts\python.exe tests/integration.py --report .local/routes-integration/integration-report.json
```

`tests/route_cases.py` расширяет прежний сквозной набор: разбор находок,
совместимость карточки, все тактики, уведомления и CRM, конкурентные повторы,
отмена и неявка, госпитализация, процедура и очный контроль, эскалация,
наблюдение с новым DOCX, пересчёт, авторизация и пять встроенных сценариев.
Покрытие проверяется против OpenAPI работающих сервисов.
Дополнительные Java-тесты воспроизводят исправленные ошибки исходной реализации.

Машинные отчёты, снимки и логи находятся только в игнорируемой
`.local/routes-integration/`; исходные медицинские документы в тесты не копируются.
