# Тестовые пациенты, сортировка и вход

## Демонстрационные пациенты

17 вымышленных пациентов создаются через настоящий backend → ML → callback:

```powershell
cd C:\hackaton\final
.\ml\.venv\Scripts\python.exe -X utf8 scripts/seed_demo_scenarios.py
```

Адрес по умолчанию — `http://127.0.0.1:8080`; для отдельного тестового стенда
добавьте `--backend http://127.0.0.1:18081`. Нужны backend, ML, PostgreSQL и
Python с зависимостями `ml/requirements-lock.txt`.

В фамилии и сокращённом имени есть `[ТЕСТ NN]`, в тексте — «ТЕСТОВЫЙ ПРОТОКОЛ».
Внешние ID начинаются с `demo-scenario-v1-`. Поиск `[ТЕСТ` или этого префикса
покажет только демонстрационные записи. Исходные документы не используются.
Повторный запуск пропускает существующие ID и сохраняет действия врача.
`--prefix demo-rehearsal-2` создаёт отдельный комплект. Автоматического сброса нет.
Если создание прервалось посередине одного сценария, повторите его с новым
префиксом: уже появившийся пациент не перезаписывается.

## Карточки с маршрутами и уведомлениями

```powershell
cd C:\hackaton\final
.\ml\.venv\Scripts\python.exe -X utf8 scripts/seed_patient_cards.py
```

Создаются 9 вымышленных пациентов с отметкой `[ТЕСТ М01]`…`[ТЕСТ М09]`.
Поиск `demo-card-v1` во вкладке «Находки» показывает этот набор. Протоколы
создаются в памяти, проходят backend → ML → callback, находки подтверждаются
от имени «Тестовый врач». Маршруты создаёт backend по действующему справочнику.
Записи на приём и переходы этапов поступают через интеграционные API.

| Метка | Сценарий |
|---|---|
| М01 | Ожидает записи, уведомление отправлено, ещё не прочитано |
| М02 | Записан к врачу, уведомление прочитано |
| М03 | Срочный маршрут, уведомление отправлено |
| М04 | Две находки, направление на госпитализацию, задача перенести дату |
| М05 | Наблюдение, ожидание контрольного УЗИ |
| М06 | Неявка, запрос обратного звонка и задача менеджеру |
| М07 | Визит состоялся, направление на диагностическую процедуру |

Сразу после создания: **11 маршрутов, 12 находок, 11 уведомлений**.
Сообщения сохраняются в локальной CRM-заглушке; реальных SMS/push нет.
Прочтения и ответы пациента также вымышленные. Глобальное модельное время
не меняется, существующие пациенты не редактируются.

Повторный запуск пропускает существующие ID и не создаёт дубликатов.
После действий врача состояния могут отличаться от исходной таблицы.
`--backend http://127.0.0.1:18081` направляет набор на отдельный тестовый стенд;
`--prefix demo-card-rehearsal-2` создаёт новый независимый набор.
Если создание прервалось, уже появившиеся пациенты сохраняются и автоматически
не перезаписываются. Отчёт: `.local/demo-patient-cards.json`.

## Сортировка

Клик по «Пациент», «Находка», «Срок записи» включает сортировку, следующий меняет
направление. Поиск и фильтры сохраняются, открывается первая страница. Сортировка
выполняется на backend до пагинации. Пустые значения всегда последние, совпадения
упорядочиваются по ID.

`GET /api/patients?sortBy=patient&sortDirection=asc`

- `sortBy`: `patient`, `finding`, `due`, `receivedAt`, `studyDate`, `default`.
- `sortDirection`: `asc`, `desc`.
- `patient` — полное ФИО по русскому алфавиту; `finding`, `due` — первая
  отображаемая находка и её рекомендованный срок.
- `default` — прежний порядок: срочность, затем время поступления.
- Неверные значения — 400. `stage` и `notified` недоступны: данных ещё нет.
  Заголовки сохраняют вид макета, объяснение показывается при наведении.

## Вход и выход из аккаунта

Единственный демонстрационный аккаунт: **логин `123`, пароль `123`**.
Самостоятельной регистрации нет, поскольку нужен один аккаунт.
Пароль проверяется через BCrypt, API его не возвращает. Сессия — HttpOnly cookie
`JSESSIONID`, SameSite=Lax, 30 минут бездействия. Перезапуск backend завершает сессии.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/auth/csrf` | `token`, `headerName`, `parameterName` |
| POST | `/api/auth/login` | JSON `{"login":"123","password":"123"}` |
| GET | `/api/auth/me` | Текущий пользователь; 401 без сессии |
| POST | `/api/auth/logout` | Завершить сессию; 204 |

Для POST нужен заголовок с именем `headerName` и значением `token`, полученными
из `/csrf`. Все запросы используют одну cookie-сессию. Вход возвращает
`{"login":"123","roles":["DOCTOR"]}`, меняет ID сессии и сбрасывает CSRF.
После входа получите новый токен. Неверные реквизиты — 401, неверный или
отсутствующий CSRF — 403. Ошибки возвращаются как `{code, message}`.

```javascript
const token = await fetch('/api/auth/csrf').then(r => r.json());
const response = await fetch('/api/auth/login', {
  method: 'POST', credentials: 'include',
  headers: { 'Content-Type': 'application/json', [token.headerName]: token.token },
  body: JSON.stringify({ login: '123', password: '123' }),
});
if (!response.ok) throw new Error('Вход не выполнен');
const account = await response.json();
// Обновить CSRF перед следующим POST, в том числе /api/auth/logout.
```

По умолчанию `AUTH_REQUIRED=true`: форма входа подключена, `/api/patients/**`,
`/api/findings/**`, `/api/protocols/**` требуют сессию, изменяющие запросы — CSRF.
Если в старом `.env` задано `AUTH_REQUIRED=false`, замените его на `true` и
пересоздайте backend. Машинные `/api/integration/**`, словарь
и health остаются открыты для ML. Это ещё не защита всех сервисов при публикации.

`AUTH_LOGIN` / `AUTH_PASSWORD` меняют единственный аккаунт. Для HTTPS используйте
`AUTH_COOKIE_SECURE=true`. CORS разрешает указанные в конфигурации локальные
frontend-адреса. Backend-переменная `AUTH_ALLOWED_ORIGINS` меняет список (через
запятую); для Docker её надо также передать в `backend.environment`. Для разных
origin все запросы, включая `/csrf`, требуют `credentials: 'include'`.

Форма входа и меню профиля перенесены из подготовленной вёрстки. Нажмите на врача
внизу слева, затем «Выйти»: backend завершит сессию, интерфейс вернёт экран входа.
Перезагрузка сохраняет действующий вход; после выхода старая cookie недействительна.
Скрипты отправки DOCX, создания тестовых пациентов и проверки системы входят сами,
используя `AUTH_LOGIN` / `AUTH_PASSWORD` (по умолчанию `123` / `123`).
