## 2. Дополнительные недостатки — НЕ исправлены

Приоритет P1 означает существенную проблему точности, восстановления или защиты
интеграций. P2 — проблему корректности, производительности или управления интерфейсом.
У каждого пункта указано, что именно подтверждено, без предположения о частоте в реальных данных.

### R1 · P1 · ML принимает условный/отрицаемый контекст за факт пациента

Место: `ml/app/clinical_v2.py:67–71,107`. `context_attributes` получает весь текст,
включая рекомендации. Для ХГЧ используется поиск совпадения без проверки отрицания;
условность рекомендаций также не учитывается.

Воспроизведение через настоящий DOCX → ML → backend:

```text
Описание
Плодное яйцо в полости матки не визуализируется.
Заключение
Беременность не установлена.
Рекомендации
При положительном ХГЧ повторить УЗИ.
```

Результат: `ECTOPIC_PREGNANCY`, `hcgPositive=true`, `uncertain=true`; backend сохраняет
находку `SUGGESTED`, уровень `EMERGENCY`, срок 0, специальность «Дежурный гинеколог».
Условная рекомендация не является подтверждением положительного ХГЧ.
Отдельный локальный прогон с «Положительный ХГЧ не выявлен» также вернул этот код.

Второй подтверждённый пример: неоднородный эндометрий 9 мм, 19-й день цикла.
Без рекомендации backend не сохраняет активной находки по действующим правилам.
Добавление «При появлении кровянистых выделений обратиться к гинекологу» даёт
`bleeding=true` и `SUGGESTED` со сроком 14 дней. Меняется решение backend, хотя
описание исследования осталось прежним.

В проверенных случаях клинические маршруты ещё не созданы: барьер подтверждения
врачом действует. Ошибка находится в предлагаемых фактах и срочности.

Предлагаемое отдельное исправление: выделить достоверный контекст пациента,
исключать условные рекомендации и применять отрицание к ХГЧ; добавить пары
положительный/отрицательный/условный контекст во все затрагиваемые профили.

### R2 · P1 · После временной недоступности словаря нет повторного анализа

Места: `ml/app/processing.py:46–50`, `ml/app/service.py:57–78,92–96`.

Проверка: поставщик словаря один раз возвращает `OSError`, затем корректный YAML.
Первое событие сохраняется как `FAILED / DICTIONARY_UNAVAILABLE`. Повтор того же
события после восстановления возвращает тот же `FAILED`; `/retry` повторяет только
доставку, а не распознавание. Поставщик вызван один раз. Независимый свежий
`process_event` с тем же документом и рабочим словарём возвращает `DONE`.

Итог: краткий сбой становится постоянным результатом протокола. Новый `eventId`
с той же версией не решает проблему из-за контроля версий. Нужен отдельный механизм
повторного анализа с сохранением идемпотентности и согласованием повторного callback
с backend; простого изменения статуса доставки недостаточно.

### R3 · P1 при внешнем доступе · Машинные интеграции не проверяют отправителя

Места: `backend/src/main/java/ru/meditron/routing/config/SecurityConfig.java:46–60`,
`ml/app/asgi.py:37–64`, `frontend/nginx.conf`.

На отдельном стенде без cookie и без CSRF:

- `GET /api/patients` → 401, защита врачебного API работает;
- корректный `POST /api/integration/protocols` → 202, создан синтетический пациент;
- `POST /api/integration/route-events` → 202, тактика существующего тестового маршрута изменена.

Исключение машинных интеграций из врачебной сессии закономерно, но отдельного
токена, подписи или проверки источника нет. Через общий nginx доступны и эти пути.
При доступности сервиса постороннему он может передавать события МИС/CRM/ML.
Текущий compose публикует порты только на localhost, поэтому это прежде всего
блокер внешнего размещения, а не утверждение об открытом интернете сейчас.

Предлагаемое отдельное исправление: аутентификация сервисов, проверка подписи
callback и ограничение доступности интеграционных путей. Аккаунт `123 / 123` —
ранее согласованное демо, в рамках этого ревью он не менялся.

### R4 · P2 · Находка в списке подписывается чужим типом исследования

Места: `backend/src/main/java/ru/meditron/routing/service/PatientQueryService.java:88–90`,
`frontend/src/pages/Patients.jsx:26–28`.

Воспроизведение: у одного синтетического пациента сначала протокол щитовидной
железы с узлом, затем отдельное УЗИ брюшной полости без находок. API списка отдаёт
`studyType=ABDOMEN`, но первым в `topFindings` остаётся `THYROID_NODULE`.
Фронтенд ставит эти значения в одну ячейку: узел щитовидной железы + УЗИ брюшной полости.
Время поступления берётся от последнего протокола и тоже может относиться к другому исследованию.

Причина: активные находки собираются по всем незаменённым протоколам, а тип и дата —
только по последнему. Нужна привязка отображаемой находки к её протоколу в DTO списка.

### R5 · P2 · Тактика принимает контрольную дату в прошлом

Место: `backend/src/main/java/ru/meditron/routing/route/service/RouteEngine.java:418,429–440`.

После перехода синтетического маршрута в `AWAITING_TACTIC` отправлена тактика
`OBSERVATION` с `controlDate`, отстающей на пять дней от модельных часов.
Ответ 202; эта дата сохранена в `controlAt` и `dueAt`, этап — `OBSERVATION_WAITING_US`.
Аналогичная отсутствующая проверка видна в ветке `ADDITIONAL_EXAM / TESTS` для `dueDate`;
именно ветка наблюдения проверена по HTTP.

В отличие от записи и даты госпитализации, новый план может сразу оказаться
просроченным и запустить соответствующие таймеры. Следует отделить импорт
исторических событий от назначения нового срока и валидировать новые даты.

### R6 · P2 · Список пациентов многократно обходит всю базу

Места: `backend/src/main/java/ru/meditron/routing/service/PatientQueryService.java:48–52,134–165`,
`frontend/src/pages/Patients.jsx:56–61`.

Backend загружает всех пациентов, затем отдельно протоколы, находки и количество
маршрутов каждого подходящего пациента. Пагинация выполняется после этого в памяти.
Даже `size=1` для счётчика требует полного прохода. Фронтенд одновременно запрашивает
страницу и отдельный список для каждого доступного фильтра и повторяет это каждые 5 секунд.

На тестовой базе из 1147 синтетических пациентов одиночные последовательные запросы
заняли 1,875 и 2,515 с при `size=1`, 3,282 с при `size=50`. Это замеры на данном
компьютере, не нагрузочный SLA; они подтверждают заметную стоимость даже малого ответа.

Предлагаемое исправление: фильтрация, сортировка, пагинация и агрегаты в БД,
пакетная загрузка зависимостей и отдельный компактный ответ со счётчиками.

### R7 · P2 · Медленная доставка одного ML-ответа блокирует приём других протоколов

Места: `ml/app/service.py:55–78,100–112`, `ml/app/backend.py:30`.

Общий `RLock` удерживается во время разбора DOCX/загрузки словаря и во время
сетевой отправки callback. В локальном тесте callback первого пациента задержан
на 1,2 с; приём другого независимого протокола занял 1,234 с вместо возможности
обработаться параллельно. По умолчанию HTTP timeout callback составляет 10 секунд.

Это ограничение становится заметным при медленной сети или пачке исследований.
Следует отделить сетевые операции от блокировки журнала, сохранив порядок событий
одного протокола и защиту от дубликатов. Исправление не выполнялось.

### R8 · P2 · Модальные окна не удерживают клавиатурный фокус

Место: `frontend/src/components/ui.jsx:18–28`.

В окне «Данные пациента» фокус установлен на последнюю кнопку. Одно нажатие Tab
переводит фокус в `BODY`, за пределы открытого окна. После Escape фокус не возвращается
на кнопку «Подробнее». `aria-modal=true` задан, но удержание/возврат фокуса и
исключение фоновых элементов из клавиатурной навигации не реализованы.

Требуется отдельное исправление общего Dialog; в этом задании изменён только цвет
фокуса, без переработки поведения модальных окон.

### R9 · P2 · Риск блокировки очереди из-за постоянно падающего таймера

Место: `backend/src/main/java/ru/meditron/routing/route/service/TimerRunner.java:62–74`.

**Вывод по коду, без внедрения повреждённых таймеров в БД.** При исключении транзакция
откатывается, самый ранний таймер остаётся `PENDING`, проход завершается. На следующем
такте выбирается он же. Если ошибка постоянная — например, сохранённый шаг цепочки
с неизвестным действием, для которого `ChainService.runStep` явно бросает исключение, —
остальные наступившие таймеры других пациентов не выполняются.

Для текущей корректной конфигурации такого сбоя не наблюдалось. Нет лимита попыток,
отложенного повтора или отдельного статуса неисправного задания. Это риск отказоустойчивости,
который следует проверить отдельным тестом с внедрением ошибки и устранить до эксплуатации.

## 3. Известные ограничения, не новые дефекты

- В общем списке «Этап» и «Уведомлён» остаются заглушками; «Просрочена запись» и
  «Без записи» отключены. «Срок записи» показывает рекомендованное количество дней
  из справочника, а не оставшееся время фактического маршрута. В карточке реальные
  маршруты и уведомления уже доступны. Это зафиксированный разрыв между двумя контрактами;
  на текущем задании новые возможности списка не добавлялись.
- Ручное редактирование/добавление маршрута на листе проверки протокола отключено;
  маршрут формируется после проверки находок. Внешний вид кнопок не означает наличие этой функции.
- Дашборд — согласованная статическая вёрстка. Статистику проекта по нему оценивать нельзя.
- CRM и расписание на тестовом стенде — эмуляторы. Успешная запись уведомления в
  outbox подтверждает внутренний цикл, но не доставку сообщения на реальный телефон.
- ML извлекает факты по правилам, без обученных весов и OCR. Новая терминология и
  описанные в YAML поля поддерживаются, новая клиническая семантика требует разработки.
- Уже известные ошибки v8 на последнем наборе сохранены: отдельные случаи роста узлов,
  типа кисты, привязки вены/кровотока и отрицательного перечисления в верхнем регистре.
  Они перечислены в `docs/ml-generalization-v8.md`; настоящее ревью их не исправляет.

### Регрессионный F1
