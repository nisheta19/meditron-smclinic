# Интеграция backend → ML → backend

## Очередь выбора направления

`GET /api/patients?needsRouteReview=true` — «Входящие»: только случаи, требующие
решения врача по направлению. `false` — остальные пациенты («Находки»).
Без параметра API возвращает обе группы. Фильтрация выполняется до пагинации;
поле `needsRouteReview` присутствует и в списке, и в `card.patient`.
Наличие неподтверждённой находки само по себе не означает неопределённый маршрут.
Не использовать `activeRoutes == 0` как признак «Входящих»: исполнение маршрутов
ещё не реализовано. Уровни срочности `EMERGENCY`, `URGENT`, `PLANNED` берутся
из YAML; `URGENT` доступен в фильтре «Срочно». Отдельных меток возле пациента
нет: цвет текста срока записи зависит от числа дней (0 — красный, 1–3 — янтарный).

## Один полный цикл

1. Отправитель передаёт DOCX и метаданные в `POST /api/integration/protocols` бэкенда.
2. Backend кодирует файл в base64 и отправляет событие в `POST /api/mis/events` ML.
3. ML читает DOCX, получает `GET /api/dictionary/findings?full=true`, извлекает факты
   и сохраняет неизменяемый результат в SQLite. Ответ 202 пока означает только приём.
4. Рабочий поток ML отправляет JSON в `POST /api/integration/ml/results` backend.
5. Backend проверяет данные, применяет YAML-правила, сохраняет пациента, версию
   протокола, находки и квитанцию в одной транзакции PostgreSQL; отвечает 202.
6. В статусе события появляется `delivery: delivered`. Пациент доступен через
   `GET /api/patients`, карточку и `GET /api/protocols/{protocolId}`.

Загрузка файла не держит транзакцию PostgreSQL во время вызова ML. Нет циклического
ожидания callback внутри исходного HTTP-запроса. Файлы не сохраняются в backend;
извлечённый текст и JSON-результаты сохраняются в PostgreSQL/SQLite локально.

## Метаданные

```json
{
  "eventId": "demo-sign-001",
  "eventType": "PROTOCOL_SIGNED",
  "patient": {
    "externalId": "demo-patient-001",
    "fullName": "Белова Наталья Олеговна",
    "lastName": "Белова",
    "firstName": "Наталья",
    "middleName": "Олеговна",
    "birthDate": "1990-01-01",
    "sex": "F"
  },
  "protocol": {
    "externalId": "demo-protocol-001",
    "version": 1,
    "studyType": "BREAST",
    "studyDate": "2026-09-11"
  }
}
```

Типы исследования: `PELVIS_FEMALE`, `ABDOMEN`, `BREAST`, `THYROID`, `PROSTATE`,
`LOWER_LIMB_VESSELS`, `KIDNEY`, `SOFT_TISSUE`. Пол `F` или `M`.
Возраст для правил backend рассчитывает на дату исследования.
ML не заменяет метаданные сведениями из DOCX и сохраняет дополнительные поля
patient/protocol в callback. Backend сохраняет поля своего DTO; произвольные
дополнительные поля пациента в его API не возвращаются.

`lastName`, `firstName`, `middleName` — необязательные строки (допускается `null`).
`fullName` остаётся обязательным для совместимости с текущим контрактом ML.
Если передана непустая фамилия или имя, backend использует части, нормализует
пробелы, пустые значения превращает в `null` и собирает из частей `fullName`.
Составное имя или фамилия остаются одним полем. Если частей нет, применяется
старое правило: первое слово `fullName` — фамилия, второе — имя, остальные — отчество.
Оно также действует при чтении старых записей базы; новые nullable-колонки
`last_name`, `first_name`, `middle_name` добавляются через Hibernate `ddl-auto: update`.
API списка и карточки отдаёт эти три поля и готовый `shortName` («Белова Н. О.»).
Фронтенд не разбирает ФИО по пробелам. Поиск работает по собранному `fullName`.
ML пересылает исходный блок `patient` без нормализации или извлечения ФИО из DOCX.

## Новые эндпоинты бэкенда

| Метод и путь | Вход | Ответ |
|---|---|---|
| `POST /api/integration/protocols` | multipart: `metadata` с Content-Type application/json; `file` DOCX | 202: eventId, resultId, status, delivery, attempts, deliveryError |
| `POST /api/integration/events` | JSON события МИС с fileName/contentBase64; для аннулирования файл не нужен | Та же квитанция 202 |
| `GET /api/integration/events/status?eventId=...` | eventId, URL-encoded | 200: обработка и доставка; 404: события нет |
| `POST /api/integration/events/retry?eventId=...` | eventId, URL-encoded | 202: повторная доставка разрешена; 404: события нет |

Для multipart используйте HTTP-клиент, корректно устанавливающий тип JSON-части.
Рабочий пример — `scripts/submit_protocol.py`. Предельный размер DOCX — 20 MiB,
multipart — 22 MiB, события ML — 29 MiB. Повреждённый DOCX даст принятый результат
`FAILED`, который также появится в backend; это отличается от ошибки формата события 400.

Пустой/неверный запрос: 400; повтор идентификатора с другим содержимым: 409;
слишком большой запрос: 413; неверный Content-Type: 415; ML недоступен: 502.
После 502 или сетевого таймаута повторяйте **тот же eventId и содержимое**: событие
могло сохраниться в ML до потери ответа. Перенаправления HTTP сервисы не выполняют.

## Исправление и аннулирование

- Подписание: `PROTOCOL_SIGNED`, новая пара patient/protocol, `version: 1`.
- Исправление: новый eventId, `PROTOCOL_CORRECTED`, те же внешние идентификаторы,
  версия больше предыдущей и новый файл. Backend сохраняет историю, снимает активные
  находки предыдущей версии; новые находки требуют проверки врача.
- Аннулирование: новый eventId, `PROTOCOL_ANNULLED`, текущая или более новая версия.
  Отправить через `/api/integration/events` без файла. Находки снимаются.
- Старая версия не должна закрыть новую. Поздний callback backend фиксирует как
  полученный, но не меняет актуальный протокол и метаданные пациента.
- Протокол с одним externalId нельзя перепривязать к другому пациенту.

Повтор одного resultId с тем же содержимым безопасен, в том числе одновременно.
Иное содержимое под тем же resultId отклоняется 409. В PostgreSQL есть уникальность
версии протокола и транзакционная блокировка приёма. Для нагрузки хакатона приём
результатов сериализован; высокая нагрузка потребует более узких блокировок.

SQLite переживает перезапуск ML. Уведомления об исправлении/аннулировании одного
протокола доставляются по порядку; отклонённый результат блокирует следующие до
разрешения ошибки. Retry повторяет доставку того же JSON, а не извлечение фактов.

## Контракты и справочник

`GET /api/dictionary/findings` возвращает прежний краткий список для frontend.
`full=true` теперь возвращает **объект** со всеми блоками исходного YAML:
`version`, `ml`, `flags`, `backend`, `routeTemplates`, `findings` и остальными полями.
Это исправление необходимо ML. Передавать краткую проекцию в ML нельзя.

Канонический YAML: `backend/src/main/resources/dictionary/findings-dictionary.yaml`.
Копия `ml/configs/findings-dictionary.yaml` должна совпадать с ним.
В live-режиме ML использует справочник backend; для CLI можно явно указать локальный.

Callback `DONE` требует conclusion, conclusionFound, findings, flags и текущую
dictionaryVersion. Цитаты и координаты проверяются относительно text; смещения
считаются в Unicode code points (как в Python), а не UTF-16 единицах Java.
Проверяются коды, studyType, атрибуты, confidence, флаги и причины notTriggered.
`FAILED` требует error; `ANNULLED` не содержит находок.

[Исходные требования к ML](ML-REQUIREMENTS.md) описывают смысл полей.
[Снимок реального backend OpenAPI](openapi-runtime.yaml) и
[снимок ML OpenAPI](openapi-ml.json) соответствуют реализованным методам.
Старый `openapi.yaml` из архива содержит и запланированные методы — не все реализованы.

## Что увидит frontend

Новая находка имеет `SUGGESTED`; врач подтверждает/отклоняет/редактирует её через
существующие API. После редактирования кода или атрибутов направление пересчитывается.
Инбокс учитывает срочные неподтверждённые находки из предыдущих независимых исследований,
а не только последнего. Такие находки доступны в истории карточки. `currentProtocol`
по-прежнему означает последний протокол, `currentFindings` — находки последнего протокола.

В проекте пока нет исполнения маршрутов и уведомлений: `routes=[]`, `routeId=null`.
Расчёт `targetSpecialty`, `targetDays`, `level` не означает, что запись к врачу создана.
