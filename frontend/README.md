# Интерфейс MEDITRON

React 19 + Vite 7. Рабочий режим обращается к настоящему backend: входящие,
фильтры и поиск, карточка пациента, текст и цитаты, версии протокола,
подтверждение, отклонение, добавление и удаление находок, маршруты и уведомления.
Списки на открытой вкладке обновляются каждые 5 секунд, сохраняя поиск, фильтры
и номер страницы. Поступивший через ML результат появляется автоматически.
ФИО берётся из контракта backend: `shortName` для списка, `lastName`, `firstName`,
`middleName` отдельными строками в карточке. Отсутствующее отчество не показывается;
составные имена и фамилии не разбиваются. `fullName` остаётся для подсказок и поиска.

## Запуск всей системы

Из корня проекта:

```powershell
docker compose up --build -d --wait --wait-timeout 180
```

Интерфейс: http://127.0.0.1:3000 . Nginx отдаёт сборку и передаёт `/api/` в
`backend:8080`. Рабочая цепочка: DOCX → backend → ML → callback → PostgreSQL → UI.
Frontend не обращается к ML напрямую. Все четыре сервиса запускаются общим Compose.
Адрес документации реализованного API: http://127.0.0.1:3000/open-api .

`FRONTEND_PORT` в корневой `.env` меняет внешний порт. Настройки Vite применяются
при сборке; переменная окружения уже запущенного nginx их не меняет.

## Разработка без frontend-контейнера

Нужен Node.js 22.12+ и работающий backend.

```powershell
cd frontend
npm ci
Copy-Item .env.example .env.local
npm run dev
```

Открыть http://localhost:5173 . В `.env.local`:

- `VITE_USE_MOCK=false` — настоящий API, значение по умолчанию.
- `VITE_API_URL=/` — запросы через общий адрес и dev proxy.
- `API_PROXY=http://localhost:8080` — backend Docker. Для `Start-Local.ps1` использовать `http://127.0.0.1:18080`.
- `VITE_DOCTOR_NAME=Демо-врач` — подпись действий для локальной демонстрации; не авторизация.

`npm run build` собирает приложение, `npm run preview` только показывает сборку:
для API используйте nginx либо задайте доступный адрес backend с настроенным CORS.

## Готовность подключения карточки

Экран входа подключён к backend; обязательный вход включён. Логин и пароль — `123`.
Нажатие на профиль врача открывает меню «Выйти»: сессия завершается на сервере,
после чего появляется экран авторизации. Перезагрузка не восстанавливает завершённую
сессию. При истечении сессии интерфейс также возвращает форму входа.
Backend вычисляет специалиста, срок и срочность из YAML. Маршруты, запись,
задачи, эскалации и заглушка уведомлений подключены на сервере;
[контракт для новой карточки](../docs/routes-integration.md). Новая карточка из
`deliverables/patient-card` подключена к `clinicalRoutes` и истории уведомлений.
Она показывает серверные этапы, сроки, запись, историю переходов и открытые задачи.
Данные карточки и сообщения обновляются каждые 15 секунд на открытой вкладке.
Нажатие на находку или исследование в истории открывает отдельный экран протокола с цитатами и
действиями врача. Заменённые версии доступны только для чтения. Старые независимые
исследования остаются редактируемыми. Закрытые маршруты доступны в истории справа.
Кнопка отправки открывает выбор маршрута и ручного шаблона из backend, а также
точный предпросмотр через `GET /api/routes/{id}/notification-preview?templateCode=...`.
Предпросмотр не создаёт уведомлений. «Сохранить и отправить уведомление» подтверждает
ожидающие находки выбранного протокола и открывает это окно; отправка требует
отдельного нажатия в нём. Ручное изменение срочности, специалиста, типа, этапа и даты
маршрута не поддерживается backend: эти элементы макета остаются отключёнными.
Повтор за
24 часа требует явного подтверждения. Ошибки сервера не подменяются пустой историей.
Реальной доставки push/SMS нет: сообщение сохраняется в заглушке CRM.
«Настройки» и «Картотека» удалены из бокового меню; старые прямые ссылки показывают
только сообщение о недоступности раздела.
Справочник используется внутри формы добавления находки. При добавлении находки
форма берёт разрешённые атрибуты из полного YAML, включая числовой BI-RADS.

Макеты списка и карточки воспроизведены по двум предоставленным CSS-экспортам
и изображениям. Inter и Manrope включены в сборку и загружаются с нашего сервера.
Недоступные функции сохранены визуально: фильтры «Просрочена запись» / «Без записи»,
в списке пациентов остаются отключёнными. Счётчики этих двух фильтров показывают 0
как заглушку, а не результат расчёта записей. Неизвестные этап, прогресс, уведомления
и контактные/антропометрические значения обозначены прочерками.
В колонке срока показан рекомендуемый интервал backend, а не вымышленная дата записи.
Чекбоксы списка выбирают строки локально; массовой записи или рассылки нет.
Поля «Дата исследования с/по» открывают календарь при фокусе или нажатии в любом
месте поля. Можно одновременно вводить дату в формате дд.мм.гггг и выбирать её
в календаре: после выбора он остаётся открыт. Enter открывает календарь,
стрелка вниз переводит фокус на дни, стрелки перемещают выбор. Escape или
нажатие вне поля/календаря закрывает его, сохраняя дату и незавершённый ввод.
Закрытие панели также сохраняет ввод; «Сбросить фильтры» очищает его.
В API отправляются только корректные даты YYYY-MM-DD; неполный ввод не заменяет
последний применённый фильтр, пустое поле снимает его. Иконки календаря нет.
У всех полей фильтров серая обводка 1 px без зелёного ореола; выпадающие меню
и календарь используют серое выделение.
В списке рядом с пациентом и находкой нет отдельных меток «Срочно»/«Экстренно».
В новой карточке статус находки показан отдельной колонкой, как в её макете.
В колонке «Срок записи» окрашивается только текст срока: 0 дней / немедленно —
красный, 1–3 дня — янтарный, от 4 дней и неизвестный срок — обычный.
Цвет зависит от показанного количества дней, а не `maxLevel`; медицинские уровни
backend не меняются. Фильтр «Срочно» со счётчиком сохранён.
В автономном демо такое же оформление; просроченный срок красный, вместо
слова «Экстренно» показано «Немедленно». Цветных боковых полос, фоновых плашек,
дополнительных подписей статуса, счётчиков находок и служебных панелей нет.
Флаги протокола и причины исключения фактов находятся в «Подробнее».
Версию/исследование можно открыть через историю справа на экране протокола;
крестик возвращает к сводке пациента.
Аватар использует фрагмент предоставленного
макета списка; данные и выводы протоколов в изображение не встраиваются.

Карточка, проверка протокола и окно уведомления оформлены по трём новым макетам.
На широком экране весь интерфейс пропорционально увеличивается от основы 1280 px:
при 1920 px масштаб равен 150%, включая текст, боковое меню и кнопки.
Узкие экраны сохраняют адаптивную вёрстку. Смена масштаба не меняет экран авторизации.

## Статичный дашборд

Пункт «Дашборд» в боковом меню открывает `/#/dashboard`. Экран повторяет
предоставленный макет 1280 × 1038: точечная карта, карточки показателей,
волна и результативность уведомлений. Данные и подписи взяты из макета,
не вычисляются и не характеризуют пациентов в базе.

Поиск, фильтры «Москва» / «За неделю» и все стрелки внутри дашборда — отключённые
заглушки. Они не открывают меню и не меняют показатели. Запросов к API пациентов и
фонового обновления нет; в рабочем режиме проверяется сессия, без backend доступен
только явный автономный режим `?mock=1`. Переходы между разделами в боковом
меню работают. По последнему уточнению пользователя во всех разделах остаются
три пункта: «Дашборд», «Входящие», «Находки». Профиль врача и «Свернуть» находятся
на одной высоте на дашборде и в списке. Режим `?mock=1` не меняет этот экран
и не добавляет в него панель управления демо.

Векторы карты и волны взяты из предоставленной вёрстки; весь текст остаётся
текстом, шрифты загружаются локально. Исходный архив и полный SVG-экспорт
в репозиторий не добавляются. Из архива не переносились backend или старая
логика расчёта показателей.

## Отдельная автономная демонстрация

Только явный `?mock=1` или `VITE_USE_MOCK=true` включает старую демонстрацию
маршрутов на вымышленных данных. Она имеет собственные условные правила,
не отправляет изменения в backend и не подходит для оценки качества ML.
`npm run static` собирает её в `dist/sm-route.html`. Ошибка сети в рабочем режиме
никогда не переключает интерфейс на заглушку. Реальные тексты из архивного
`samples.json` удалены; исходный ZIP не изменён.

## Проверки

Чтобы вымышленные записи не попадали в рабочий интерфейс, сначала запустите
отдельный стенд с собственными томами PostgreSQL и ML:

```powershell
docker compose -p meditron-verification -f docker-compose.yml -f compose.verification.yaml up --build -d --wait
```

```powershell
cd frontend
npm ci
npm test
npm run build
npx playwright install chromium
cd ..
.\ml\.venv\Scripts\python.exe -X utf8 tests/frontend_fixtures.py
cd frontend
$env:FRONTEND_URL='http://127.0.0.1:13000'
npm run test:e2e
npm run test:design
npm run test:dashboard
node tests/filters.mjs
node tests/auth-browser.mjs
node tests/patient-card-live.mjs
node tests/ui-review.mjs
node tests/finding-actions.mjs
```

Требуется отдельный Docker-проект `meditron-verification`. Подготовка по умолчанию
обращается к `http://127.0.0.1:13000` и создаёт новые
вымышленные DOCX и проводит их через nginx, backend и ML. Перед повторным E2E
запуском повторите `frontend_fixtures.py`: тесты подтверждают и отклоняют находки.
Для установленного Edge вместо скачивания Chromium можно задать
`$env:BROWSER_CHANNEL='msedge'`. `UI_FIXTURES` задаёт путь к JSON подготовленных
тестовых записей; `FRONTEND_URL` — адрес интерфейса. Результаты и снимки — в `.local/`.

`ui-review.mjs` проверяет 14 замечаний к оформлению: нейтральный фокус, имя пациента,
стрелки и сетки, отсутствие заранее выбранной сортировки и лишнего нижнего отступа,
раскрытие реальной истории и пояснения в «Подробнее». Ответы API полностью вымышлены,
запись пациентов запрещена. Отчёт и снимки сохраняются в `.local/ui-review/`.
Результаты общего ревью, включая оставленные без исправления недостатки:
[ревью 05.10.2026](../docs/review-2026-10-05.md).

Дополнительные правки из Word: после подтверждения находки статус показан обычным
текстом, галочка и крестик заменяются меню «Редактировать / Удалить». Меню доступно
в проверке протокола и у отдельной ручной находки. Редактирование использует текущий
словарь и `PATCH /api/findings/{id}`, сохраняет подтверждение врача; срочность
пересчитывает backend по атрибутам, прямого переключателя срочности нет.
Панель выделения использует обычное начертание счётчика и одинаковые отступы 12 px.
Кнопка «Демо» остаётся только в явном автономном режиме `?mock=1`.
`finding-actions.mjs` проверяет эти состояния, сетку колонок, клавиатуру и меню
при ширине 390/1280/1920 px. Отчёт и снимки: `.local/finding-actions/`.
Реальное подтверждение, редактирование и удаление проверяют `e2e.mjs` и
`patient-card-live.mjs` на отдельной тестовой базе. Не запускайте их одновременно
с интеграционной проверкой маршрутов: она временно переводит часы симулятора.

`test:design` отдельно проверяет размеры двух макетов при ширине 1280 px,
выбор строк, отключённые заглушки, цитаты и адаптивность при 390/768/1024/1280/1920 px.
Отдельно проверяются цвета сроков 0/1/2/3/4/7 дней независимо от уровня,
неизвестный срок и отсутствие меток срочности/прочих украшений для
подтверждённых, отклонённых, ручных и помеченных флагами находок.
В этом тесте ответы API подменяются полностью вымышленными данными из
`tests/design-fixtures.mjs`, БД не меняется. Снимки `.local/design-list.png` и
`.local/design-patient.png` предназначены для визуального сравнения.
Реальные запросы и сохранение изменений проверяет `test:e2e`.
`test:dashboard` проверяет геометрию макета, цифры и графики, отключённые элементы,
отсутствие запросов при заблокированном API, переходы через боковое меню и
адаптивность. Снимок `.local/dashboard-final.png` сравнивается с пользовательским
макетом при одинаковом размере 2560 × 2076 (1280 × 1038, DPR 2).
Машинный отчёт: `.local/dashboard-results.json`.
`node tests/filters.mjs` проверяет ручной ввод, сохранение даты/черновика, фокус календаря,
переходы месяцев, границы дат для API, сброс, серые состояния и нулевые счётчики.
Он использует вымышленные ответы API, БД не меняется. Отчёт и снимки:
`.local/filter-controls-results.json`, `.local/filter-controls*.png`.

Для сверки трёх макетов запустите Vite на порту 5173 и выполните
`node tests/three-layouts-visual.mjs`. Проверяются размеры протокола и модального окна,
положение кнопки сохранения, увеличение при 1920 px и отсутствие переполнения.
Снимки и координаты — в `.local/three-layouts/`; данные макета существуют только
в тестовом стенде и не входят в рабочую базу.

Структура: `src/api` — HTTP и отдельное демо; `src/pages` — экраны;
`src/components` — формы и компоненты; `src/lib/evidence.js` — Unicode-цитаты;
`src/lib/findingFields.js` — поля YAML; `tests` — модульные и браузерные проверки.

## Очереди пациентов

«Входящие» запрашивает `needsRouteReview=true`, «Находки» — `false`.
Решение принимает backend до пагинации и подсчёта счётчиков. Во «Входящих»:
ошибка обработки, отсутствие заключения, недостаточные/неоднозначные данные,
неполное направление или `MANUAL_REVIEW`. Уже рассчитанные направления без
таких проблем остаются в «Находках», даже если находка ещё `SUGGESTED`.
После подтверждения/отклонения неоднозначных находок очередь пересчитывается.
Подтверждение `MANUAL_REVIEW` само по себе не задаёт специалиста и не скрывает
пациента из очереди. Аннулированные и заменённые версии её не блокируют.
Нормальный протокол без находок во «Входящие» не попадает.
Это очередь выбора направления; этапы исполнения маршрута доступны в карточке.

Сортировка включается заголовками «Пациент», «Находка», «Этап», «Срок записи»,
«Уведомлён»; backend сортирует весь результат до пагинации. «Этап» сортируется
по проценту прохождения, «Уведомлён» — по последней успешной отправке. Пустые
значения остаются в конце при обоих направлениях сортировки.

`GET /api/patients` возвращает `tracking`: маршрут первой находки в строке,
`stage` / `stageTitle`, `progressPercent`, `lastNotifiedAt`, `notificationCount`.
Для маршрутов и уведомлений выполняются два пакетных запроса; дополнительных
запросов карточки или истории для каждой строки frontend не делает.
При нескольких маршрутах используется связанный с первой находкой открытый,
иначе последний связанный закрытый. Если у этой находки маршрута нет, полоса
пустая, без выдуманного процента. Название этапа видно в подсказке над полосой.

Процент — доля зафиксированных шагов из `listProgress` в
`backend/src/main/resources/routing/route-config.yaml`, отдельно для консультации,
хирургии, наблюдения и процедуры. Повторы не увеличивают процент; при смене ветки
он пересчитывается. Завершённый маршрут или решение «операция не показана» даёт
100%; отказ, отмена и аннулирование не приравниваются к успешному завершению.
Это индикатор выполнения маршрута, не оценка здоровья и не доля прошедшего времени.

«Уведомлён» показывает последнюю отправку и число сообщений по всему пациенту,
включая прошлые маршруты. Учитываются SENT / DELIVERED / READ, FAILED исключён;
повторный callback доставки не увеличивает счётчик. Без сообщений отображаются
«Не уведомлён» и «0 уведомлений». Если модуль маршрутов отключён и `tracking=null`,
показаны прочерки. Данные обновляются вместе со списком каждые 5 секунд.

`node tests/list-tracking-visual.mjs` проверяет макет и пустые состояния на
вымышленных ответах. `node tests/list-tracking.mjs` проверяет реальную цепочку
подтверждение → маршрут → отправка → CRM → запись → завершение и сортировку.
Последний тест запускается после `integration.py`, на свежем отдельном наборе
`frontend_fixtures.py`. Снимки и результаты: `.local/list-tracking/`.
[Тестовые пациенты и контракт входа](../docs/demo-and-auth.md).
После создания тестовых пациентов `node tests/sorting.mjs` проверяет обе стороны
сортировки в браузере; для другого префикса пациентов задайте `SCENARIO_PREFIX`.

## Проверки авторизации

Вёрстка перенесена из `deliverables/auth-adaptation`; изображения и шрифты локальные.
API пациента требует cookie-сессию, действия врача дополнительно требуют CSRF.
Клиент обновляет CSRF после входа; пароль и cookie не сохраняются в localStorage.
Скрипты подготовки данных и E2E сами входят через API. Для другого аккаунта задайте
`AUTH_LOGIN` и `AUTH_PASSWORD` одновременно серверу и тестовым скриптам.

```powershell
$env:FRONTEND_URL='http://127.0.0.1:13000'
$env:BROWSER_CHANNEL='msedge'
node tests/auth-browser.mjs
node tests/auth-live.mjs
node tests/auth-visual.mjs
```

`auth-browser` проверяет состояния UI с подменёнными ответами; `auth-live` проверяет
настоящие cookie, CSRF, вход, выход и истечение сессии на отдельном Docker-стенде.
`auth-visual` снимает пустую и заполненную формы при 1280 × 832, DPR 2.
Для отдельного снимка меню запустите Vite, затем задайте его адрес в `FRONTEND_URL`
и выполните `node tests/profile-visual.mjs`: ему нужна тестовая HTML-страница.
Отчёты и снимки сохраняются в `.local/auth-integration/` в корне проекта.
